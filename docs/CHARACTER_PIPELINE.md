# キャラクターの企画・実装・効果検証

2026-10-28の所有者指示：キャラをゲームへ組み込み、今後の自動開発にも新キャラを考えて組み込む工程を加える。
顧客獲得の利点と開発負荷を一緒に評価する。人気作の仕組みから学び、簡単な形でも魅力が残る外観を設計する。

## 現在の範囲

この変更案は工程と、最初の1体キュアボを一緒に検証する導入パイロット。
キュアボは選択・有料ではない試合内コインでの生産・修理・モデル生成を持つオフライン試作。
残る8体は `config/characters.json` の `candidates`。実装済みの `characters` と分ける。
12体という人数に色違い、スキン、JUNK、敵ボス、案内NPCは含めない。
永続解放、課金、試合前3体装備、PvP、協力、実機での外観や面白さは、このパイロットの実装に含まれない。

## 既存体制で回す工程

| 工程 | 担当 | 保存・合格条件 |
| --- | --- | --- |
| 人気作・顧客反応の調査 | META | 公式出典と閲覧日、観察事実、採用する原理、自作への仮説を分ける |
| 顧客メリットと負荷の評価 | META | 新規獲得・再訪・戦略の仮評価と、モデル・動き・戦闘・UI・QAの負荷を記録 |
| 簡単な形で試す | WORKER | 大きな輪郭の特徴、32/64pxでの識別、パーツ数と動きの予算。画像生成絵だけで合格にしない |
| 小さくゲームへ接続 | WORKER | 原則1体1PR。許可済みLua範囲で選択・価格・生産・モデル・戦闘・説明を同じIDで接続。カタログ更新は含めない |
| カタログへの実装反映 | CONTROLLER | 新キャラのメタデータ変更は独立レビュー対象の別DRAFTで行い、同じIDとLuaの登録内容を照合。WORKERの自動編集権限とは分ける |
| 実行検査と配布物 | WORKER | 正本Luaを実行し、弱点・上限・不正入力・他工場・既存キャラを検査。installerの完全性を確認 |
| 独立審査・本体反映 | REVIEWER | 別task/run、現在headの両CI、共有所有権、差分とサイズを確認。統合後のmainも検査 |
| 実機・顧客効果の確認 | METAが結果を点検 | Roblox/スマホの実測、任意の試遊、獲得・再訪。未取得ならNOT_RUN/NOT_MEASURED |

3役を増やさず、登録済みWORKER/META/REVIEWERと共有ロックを使う。
新しい並列の書き込み担当、別の定期タスク、外部モデル契約は追加しない。
main障害と具体的な差戻しは先に修復する。既存作業中は待機し、手動の「続けて」で追い越さない。
固定人数の検査を外す際も、既存3体の保持・設定/実コード一致・役割・輪郭・色の検査を残す。
設定だけ増やした状態は実装完了ではない。WORKERは許可済みゲームLuaだけを小さく実装し、カタログ上の実装済みへの移動は別のCONTROLLERによるDRAFTと独立審査を経てから行う。

## 外観と実行負荷

Robloxだから必ず粗い外観になるわけではない。本作はスマホ上で多数を生産するので、最初は少ない基本パーツでつくる。
細かい金属傷、反射、複雑な歯車ではなく、大きなハート・U字磁石・コマ・バネ足を見せる。
通常候補の初期目標は18パーツ以内、大型候補は24パーツ以内。これは本作の試作予算で、Robloxの公式上限ではない。
実機では20体/陣営×4工場を考慮し、フレーム時間・メモリ・描画とネットワーク負荷を基準端末で測る。
キーの回転などの飾りは、サーバーの戦闘判定とは分けて、必要なときだけ動かす案を優先する。

キュアボの試作は17パーツ。顔、ピンクのハート、工具かばん、巻き鍵で識別する。
データ上の役割は低火力の支援。3秒間隔で1体を8HP修理し、自己・敵・死んだ仲間・他工場は対象にしない。
同じ対象への修理は共有クールダウン。満タンを超えず、回復でコイン・撃破報酬・拠点HPを増やさない。
既存3体の性能・価格は変えない。新キャラの32 coins等はプレイ検証前の初期仮説。

選択UIは3個の大きな玩具ボタンを維持し、ページ切り替えで4体以上へ対応する。
ページ操作はゲームコマンドを送らない。初回案内が閉じるまでページ操作を隠し、案内との重なりを避ける。
これは試合前の3体装備の実装ではない。装備方式は別の小さな実験にする。

## 顧客メリットと負荷の記録

`python3 tools/system_character_pipeline.py` が候補の仮評価を出す。
benefit=(新規獲得×2＋再訪×2＋戦略)。各1～5点。effortはモデル/動き/戦闘/UI/QAの作業点の合計。
priority=benefit/effortは選択の参考で、収益予測・人時・客観的な人気度ではない。
キュアボは新しい支援役を少ない機構で試せるので最初のパイロットにした。次の候補は毎回再評価する。
飛行・潜行・設備は経路や上限の検証が増えるため、見た目が良くても負荷を別途見積もる。

各PRの新規C履歴には以下を加える。過去の受理済み記録を書き直さない。
- 顧客獲得の仮説、再訪の仮説、出典、estimated_effort_points。
- 実際に変更した機能、モデルのパーツ数、未実装の演出、影響したキャラ。
- 計測できた実働秒と経過秒の区別。中断中を実働へ足さず、不明な過去時間はnull。
- 実際の検査数、旧ソース/機能を無効にした負の対照、CI/レビュー/main証拠。
- 新規プレイヤー・初回製造到達・再挑戦・翌日再訪。取得できなければNOT_MEASURED。

公開後にデータを取る場合も、キャラの絵だけでゲーム全体の効果を帰属させない。
自然流入と告知経由を分け、比較した版と露出期間を残す。広告費・公開・課金をこの工程から自動承認しない。
レア度には造形、組立演出、入手する道のりを反映し、戦闘力の一律倍率を付けない。

## 導入の審査

今回の `repository_gate.py` と `config/autonomous_repair.json` の変更は保護された導入変更。
作者のCI成功だけでは採用しない。正確なheadとbaseを指定し、別の登録REVIEWERの読取専用審査を受ける。
承認後のCONTROLLERによる導入とmain QAは、通常のWORKERによる新キャラ追加とは別に記録する。
PR #199の統合安全対策では、WORKERによる `config/characters.json` の編集許可拡張は採用しない。WORKERの編集範囲は既存のゲームLua 3ファイルと新規回帰テスト/履歴に限定する。カタログ更新は別のCONTROLLERによるDRAFTと独立レビューを必要とし、保護設定やaccepted testsを拡張して迂回しない。
現行の品質・費用・公開・Gemini停止・共有ロック・別task/run審査を維持する。
