# 完成までの小さな検証可能な道筋

2026-10-25の所有者方針：承認判断は助手へ全権委譲。完成までの長い道のりを丁寧に自動で詰める。
この順序は暫定であり、日次点検が実測・最新の一次資料・プレイヤーの反応から更新する。
ソース量、PR数、検査だけの追加を完成度に置き換えない。根拠のない完成率は出さない。

| 段階 | 合格に必要な結果 | 現時点 |
| --- | --- | --- |
| 正常なmain | 受理済みの挙動/安全性/実装検査が通り、失敗mainを優先修復できる | オフライン検査あり。床の修正と生産/ウェーブ/敗北/アップグレード検査を統合 |
| 遊べるPvE一周 | 入場→3種の玩具選択→生産→戦闘→工場強化→敗北/再試行を実際のエンジンで一周 | Lua mocksで一部検査。実機一周は未実施 |
| 複数人とスマホ | 2クライアント以上の独立状態、権限判定、スマホ操作/表示/フレーム時間を実測 | 未実施。Issue #3の実行環境が必要 |
| 工場戦略とキャラ品質 | ポン/ガードン/タンクルの役割が画面/挙動で分かり、製造戦略が結果を変える | prototype。設定の役割と実装済み能力を混同しない |
| 継続して遊べる品質 | 導線、進行/保存の必要性、難易度、再挑戦、体験上の詰まりを実プレイで確認 | 未実証。最小実験に分ける |
| 後続の協力/PvP | 遊べるPvEを土台に、元の製品構想の協力・試合限定設計図などを独立実験 | 計画。実装済みとは扱わない |

最初の到達点は、実機で一周できるPvEの検証版。その後も製品構想と品質条件へ近づける。
課金/公開などで未完成の品質を代替しない。競合作品のソースやアセットをコピーしない。

## 各実行で行うこと

1. main/自分のPRの失敗と共有WORK_REQUESTSを先に修復する。
2. 最も完成に寄与する小さな欠陥修正/実装を1件選び、再現/成功条件を決める。
3. 正本のコードを実行する回帰検査と正確な履歴/サイズ差分を付けてdraft PRへ。
4. 別タスクの審査役が検査と実差分を読み、自動で取り込み、そのmainを検査する。
5. 日次点検が採用した効果・再発・停滞を調べ、次の課題や体制そのものを更新する。

検査だけの回は検査拡充、WEBを読んだだけなら調査、コードが変わっても実機未検証ならそのまま記録する。
役割の偏り、承認待ち、ループ、無効な検査などで進行が詰まれば、それ自体を改善課題にする。

## 実行環境の不足

Robloxエンジン/複数人/スマホの証拠が今の接続で取れなければ、具体的な不足と、
所有者にPC作業を要求しない実行方法を調べる。推測で成功扱いせず、可能な独立課題は進める。
必要なアクセスと、通常の承認返信は別物。使える接続/権限は直接確認し、秘密をIssueへ書かない。
